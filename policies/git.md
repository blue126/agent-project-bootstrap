# Git and GitHub policy

## Authority and authorization

- When `origin/main` exists, it is the eventual code authority. Fetch and compare before publishing work.
- Do not assume an `origin` remote, a GitHub repository, or even an initialized Git repository exists.
- Never develop, commit, or push directly on `main` or `master`. Create a purpose-specific branch first.
- Do not create commits, push branches, open pull requests, or mutate remote state without user authorization.
- Standard stateless onboarding may explicitly create or connect a repository using `--create-only` or `--attach-only`; it does not stage, commit, or push. Re-running onboarding reinspects actual state, not a saved wizard position.
- The separate legacy explicit bootstrap `--create-github` invocation, with repository and visibility supplied by the user, authorizes only its generated bootstrap commit, repository creation, `origin`, and initial `main` push. This exception does not authorize unrelated files or bypass the pre-commit review below.
- Installing this policy is not evidence that the first commit's contents have been reviewed or verified. Report policy installation, asset review, local validation, CI, review, and protection as separate evidence; leave missing evidence pending or blocked.
- Do not discard, overwrite, or rewrite user work unless the user explicitly authorizes the exact destructive action. A merged branch or pull request never justifies deleting uncommitted, untracked, or ignored work; inspect and preserve it before branch or worktree cleanup.

## Decide by purpose, not by path or producer

Track durable assets needed to understand, reproduce, operate, or maintain the shared project, subject to sensitivity and license review. Being generated, hidden, underscore-prefixed, installed by an Agent, or located in an `output` directory is not a reason by itself to exclude a file.

| Asset purpose | Default treatment |
| --- | --- |
| Shareable project instructions, Skills, agents, hooks, commands, workflows, and portable project settings | Track the reviewed shared configuration and code, including assets in hidden directories. Keep personal overrides separate. |
| Dependency lockfiles and other reproducibility metadata | Track when used to reproduce the project's dependencies or tooling; distinguish these from temporary runtime locks. |
| Formal requirements, designs, architecture decision records (ADRs), project research, and sanitized validation/review evidence | Track reviewed, durable project records even if generated by a tool. Remove sensitive content and confirm redistribution rights first. |
| Credentials, tokens, private keys, personal overrides, conversation transcripts, personal assessments, and persistent user memory | Exclude from Git. Publish only a separately reviewed, sanitized project record where appropriate, never the private source material. |
| Runtime logs, runtime databases, PID files, mutex/lock state, caches, and reproducible build artifacts | Exclude with purpose-specific paths or patterns. A database fixture or required release asset may instead be a reviewed project asset; its extension is not the decision. |
| Nested worktrees and machine-specific/nonportable configuration | Exclude; share portable templates or documented setup instead. Do not accidentally stage a nested repository as project content. |

Third-party tooling may either be tracked after provenance, license, and sensitivity review, or reproduced through a documented bootstrap pinned to an immutable commit or content digest, with the release version recorded where applicable and downloaded content verified against the pin. Record the source and exact pin, preserve required notices, and verify that a fresh installation reconstructs the expected assets. A floating ref, an undocumented local installation, or an untested download command is not a reproducibility substitute. Existing integration-specific runtime and licensing rules still apply; this policy does not authorize installation or redistribution.

Treat shared instructions and automation as code: review invoked commands, network destinations, downloads and their verification, and permission changes before accepting them. Portable settings must not embed credentials, personal paths, or host-specific assumptions. Track a symlink only after verifying its relative, in-repository tracked target, the target's contents, and behavior on supported platforms; reject broken, absolute, escaping, or machine-dependent links. A symlink does not make an untracked external installation reproducible.

## Ignore rules and existing projects

- Preserve existing ignore rules by default. Inspect their effects, explain proposed changes and the assets they expose or hide, and obtain confirmation before changing them. Do not silently remove a rule or force-add a hidden asset to bypass it.
- Use narrow, purpose-specific exclusions. Do not introduce blanket `/.*`, `/_*`, `*.lock`, `output/`, or `*.db` rules: these can hide shared settings, formal deliverables, dependency locks, or fixtures. Review an existing broad rule with the user rather than automatically rewriting it.
- For mixed Agent directories, use explicit local exclusions or a reviewed local allowlist maintained for the tools actually used. When negating nested ignore rules, unignore parent directories before children. New shared directories require checking the allowlist; never assume a hidden directory is personal state.
- Prefer framework-local ignore files for caches and temporary renderings. Keep BMad configuration/customizations reproducible and formal `_bmad-output/` requirements, designs and research reviewable; do not exclude them by directory name alone. Do not add irrelevant language/framework templates.
- Share portable launch/configuration files through repository-relative paths, parameters, environment variables or local overrides. Review settings individually before migrating personal configuration into shared configuration; never default to unrestricted permissions, disabled sandboxing or approval bypasses just to reduce prompts.
- `.gitignore` is neither a secret scanner nor a security boundary. It does not untrack files already in Git, prevent force-adding files, or remove secrets from history. Review content independently; if sensitive data is found, stop publication and report safe remediation without exposing the secret or rewriting history without authorization.

If committed credentials are discovered, stop further propagation. Revocation/rotation and any history cleanup require their own explicit authorization; changing ignore rules does not remediate an exposed credential. Do not stash, untrack, delete or commit unrelated work as part of bootstrap. Preserve and report unknown files, and restrict cleanup to confirmed regenerable artifacts in the authorized scope.

## Pre-commit asset review

Before any commit, including an initial or bootstrap-generated commit:

1. Inspect the repository root, branch, worktrees, status, tracked and untracked files, and relevant ignored paths. Explain what will be tracked, excluded, or reproduced and why; surface conflicting ignore rules, existing staged changes, and unresolved sensitivity or license questions.
2. Inspect candidate files and their full content, not just filenames or a diff summary. Check hidden assets, symlinks and their targets, nested repositories/worktrees, and unexpectedly large files or binaries. Do not recurse into or publish another worktree by accident.
3. Review shared instructions and automation for command, network, download, and permission impact. Validate changed configuration syntax/schema and portable references using the project's applicable tools.
4. Run the project's secret scan over the intended commit content. Verify that its configuration is valid and its coverage includes the selected hidden/generated assets; do not treat an absent scanner, invalid configuration, skipped paths, or an unrun check as a pass. Report gaps and resolve them before claiming verification or publishing.
5. Stage only explicitly reviewed paths belonging to the authorized change. Never use broad staging such as `git add .` or `git add -A`; preserve unrelated staged and unstaged work and ask about conflicts rather than silently modifying it.
6. Inspect the final staged file list and complete staged diff/content, including symlink modes/targets, deletions, and binary/large-file handling. Re-run affected checks if content changes. Report validation and scan results, limitations, and the track/exclude/reproduce decisions before requesting any missing commit or publication authorization.

## First-publication acceptance

A fresh checkout must reproduce the project's Agent capabilities through the documented process. Formal project assets must be committed, not merely present on disk; credentials, personal state, caches and nested worktrees must not be included. Existing user work must be preserved and the inclusion/exclusion decisions reviewable. Policy installation and ignore-rule preparation alone do not meet these publication criteria. Add CI secret scanning when the project supports it, without treating it as a substitute for the local pre-publication scan.
